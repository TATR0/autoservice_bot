# 🚗 AutoService Bot

Телеграм-бот для онлайн-записи в автосервис.  
Стек: **Python + aiogram 3 + asyncpg + FastAPI + PostgreSQL**, всё в Docker на своём VPS

---

## Архитектура

```
autoservice_bot/
├── app.py              # точка входа: бот, REST для формы и статика — один процесс
├── config.py           # все переменные окружения
├── database.py         # asyncpg-слой, все SQL-запросы
├── keyboards.py        # все клавиатуры бота
├── schema.sql          # SQL-схема, применяется сама при выкате
├── requirements.txt
├── .env.example
├── handlers/
│   ├── start.py        # /start, deep-link SVC_
│   ├── register.py     # регистрация сервиса (FSM)
│   ├── admin_mgmt.py   # добавить / удалить администратора
│   ├── requests.py     # WebApp-заявки + «Мои заявки»
│   └── admin_actions.py# статусы, просмотр, fallback
├── webapp/
│   └── index.html      # Telegram WebApp (фронтенд)
├── docker-compose.yml  # бот, база, резервные копии
├── docker-compose.vps.yml  # надстройка для VPS: HTTPS через Caddy
└── scripts/
    ├── init_env.sh     # .env: сгенерировать секреты перед первым выкатом
    ├── deploy.sh       # выкат и обновление одной командой
    ├── import_dump.sh  # залить дамп: переезд и восстановление
    ├── backup_db.sh    # снимки базы, запускается сервисом backup
    └── backup_offsite.sh  # вывоз снимков с машины, сервис offsite
```

## Роли

| Роль | Как получить | Возможности |
|---|---|---|
| **Пользователь** | Любой, кто открыл бота | Записаться в сервис, смотреть свои заявки |
| **Администратор** | Назначается управляющим | Видеть заявки сервиса, менять статусы |
| **Управляющий** | Зарегистрировал сервис | Всё вышеперечисленное + добавлять/удалять администраторов |

Роли определяются **динамически при каждом /start** — отдельной таблицы ролей нет.  
Управляющий = `services.owner_id == tg_id`.  
Администратор = активная запись в `admins`.

## Быстрый старт

### 1. Создать бота в Telegram

1. Открыть [@BotFather](https://t.me/BotFather)
2. `/newbot` → задать имя и username
3. Скопировать токен
4. `/setprivacy` → выбрать бота → `Disable` (чтобы бот видел все сообщения)

---

### 2. База данных

Заводить ничего не нужно: PostgreSQL поднимается рядом с ботом, контейнером
`db` из `docker-compose.yml`. Из интернета он недоступен: порт открыт только
на `127.0.0.1` самой машины, то есть для контейнеров проекта и для того, кто
пришёл на сервер по SSH. Данные лежат
в томе `pgdata` и переживают `docker compose down`, пересборку и обновление
образа; удаляет их только явное `docker compose down -v`.

`schema.sql` применяется сам: при первом старте — из
`/docker-entrypoint-initdb.d`, дальше на каждом выкате, потому что скрипт
идемпотентный и забытая миграция выглядит как случайно пропавшая половина
бота.

Пароль базы генерирует `./scripts/init_env.sh` (шаг 3) и подставляет его
сразу в `POSTGRES_PASSWORD` и в `DATABASE_URL`. Если правите руками — правьте
в обоих местах: расхождение проверка перед выкатом покажет, но исправлять его
за вас не станет.

Внешняя база тоже годится — впишите её строку в `DATABASE_URL`, и контейнер
`db` просто останется невостребованным. Про переезд с такой базы на свою — в
разделе «Резервные копии».

#### Заглянуть в базу с ноутбука

Открывать порт наружу для этого не нужно и не стоит: SSH уже даёт защищённый
канал, а pgAdmin умеет ходить через него сам.

**pgAdmin 4.** Правая кнопка на `Servers` → `Register` → `Server`:

| Вкладка | Поле | Значение |
|---|---|---|
| General | Name | любое, скажем `autoservice VPS` |
| Connection | Host name/address | `127.0.0.1` |
| Connection | Port | `5432` |
| Connection | Maintenance database | `autoservice` |
| Connection | Username | `autoservice` |
| Connection | Password | из `POSTGRES_PASSWORD` в `.env` на сервере |
| SSH Tunnel | Use SSH tunneling | включить |
| SSH Tunnel | Tunnel host | IP вашей VPS |
| SSH Tunnel | Tunnel port / Username | `22` / `root` |
| SSH Tunnel | Authentication | пароль или файл ключа |

`127.0.0.1` в Connection — это не ваш ноутбук: адрес читается уже со стороны
сервера, куда pgAdmin попал по SSH.

**psql или любой другой клиент.** Прокинуть порт руками и ходить на него:

```bash
ssh -L 55432:127.0.0.1:5432 root@<ip-вашей-vps>
psql -h 127.0.0.1 -p 55432 -U autoservice -d autoservice
```

Пароль посмотреть на сервере: `grep ^POSTGRES_PASSWORD= .env`.

### 3. Поднять бота на VPS

Нужен сервер с публичным IP (одного гигабайта памяти достаточно) и домен, у
которого A-запись смотрит на этот IP. HTTPS обязателен: на http Telegram
вебхук не поставит.

```bash
# 1. Docker (Ubuntu / Debian)
curl -fsSL https://get.docker.com | sh

# 2. Код
git clone <репозиторий> /opt/autoservice_bot
cd /opt/autoservice_bot

# 3. Настройки
./scripts/init_env.sh    # создаст .env, сгенерирует секрет вебхука и пароль базы
nano .env                # BOT_TOKEN, BOT_USERNAME, DOMAIN, BASE_URL, ACME_EMAIL, BOT_OWNER_IDS

# 4. Выкат
./scripts/deploy.sh
```

`deploy.sh` собирает образ, поднимает базу и применяет к ней `schema.sql`,
проверяет `.env` и схему, поднимает бота вместе с Caddy, дожидается ответа
`/healthz` и спрашивает у Telegram, встал ли вебхук. Обновление — та же команда: `git pull && ./scripts/deploy.sh`. Сборка
идёт до остановки работающего бота, поэтому неудачная сборка ничего не гасит.

Наружу открыты только 80 и 443 — их слушает Caddy; сам бот доступен лишь с
самой машины по `127.0.0.1:8080`. Брандмауэр:

```bash
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable
```

Сертификат Caddy выпускает и продлевает сам, ключи лежат в томе `caddy_data`.
Порт 80 нужен не только для редиректа: по нему проходит проверка домена, без
которой сертификат не выдадут.

**Если 443 уже занят** — VPN, чужой веб-сервер, — бот переезжает на другой
порт. Выбирать не из чего: Telegram доставляет вебхук только на 443, 80, 88 и
8443. В `.env`:

```
HTTPS_PORT=8443
BASE_URL=https://bot.example.com:8443
```

`DOMAIN` остаётся без порта — он про имя в сертификате. Порт 80 всё равно
должен быть открыт: по нему Caddy подтверждает домен. Проверка перед выкатом
не пропустит ни порт, которого Telegram не знает, ни расхождение `HTTPS_PORT`
с адресом в `BASE_URL`.

Конфигурация для Render осталась в `render.yaml` — на VPS она не используется
и ничему не мешает.

### 4. Форма записи

Отдельный хостинг фронтенду не нужен: `app.py` монтирует папку `webapp/` на
`/app/`, и форма открывается по адресу `BASE_URL/app/` — на том же домене, что
и API. Это не только проще: при другом домене пришлось бы ослаблять CSP,
которая сейчас разрешает запросы только к своему источнику.

### 5. Переменные окружения

| Переменная | Обязательна | Что это |
|---|---|---|
| `BOT_TOKEN` | да | Токен от @BotFather |
| `DATABASE_URL` | да | Строка подключения; для своей базы — `...@db:5432/...?sslmode=disable` |
| `POSTGRES_PASSWORD` | да | Пароль базы в контейнере; тот же, что в `DATABASE_URL` |
| `POSTGRES_USER` `POSTGRES_DB` | нет | По умолчанию `autoservice` и там, и там |
| `DOMAIN` | да | Имя домена без схемы: `bot.example.com` |
| `BASE_URL` | да | Он же целиком: `https://bot.example.com`, с портом если он не 443 |
| `HTTPS_PORT` | нет | На чём слушать HTTPS. 443 по умолчанию |
| `WEBHOOK_SECRET` | да | Случайная строка: и часть URL, и заголовок Telegram |
| `BOT_USERNAME` | да | Без `@`; из него собираются ссылки `t.me/<bot>?start=...` |
| `BOT_OWNER_IDS` | да | Кому доступны `/extend`, `/refund`, `/revoke` |
| `TRUST_PROXY` | за Caddy — да | Откуда брать адрес клиента для лимитов частоты |
| `ACME_EMAIL` | желательно | Письмо, если с сертификатом что-то не так |
| `PAYMENT_METHOD` | нет | `stars` (по умолчанию) или `yoomoney` |
| `YOOMONEY_WALLET` | для `yoomoney` | Номер кошелька, на него собирается ссылка |
| `YOOMONEY_NOTIFY_SECRET` | желательно | Секрет уведомлений: без него дни начисляются руками |
| `MASTER_CHAT_ID` | нет | Чат для «потерянных» заявок |
| `TEST_DATABASE_URL` | нет | База для прогона тестов, отдельная от боевой |

Полный список с пояснениями — в `.env.example`. Что из этого не заполнено или
заполнено неправдой, скажет проверка перед выкатом:

```bash
docker compose run --rm --no-deps app python scripts/preflight_deploy.py
```

Её же вызывает `deploy.sh`, поэтому забытый плейсхолдер секрета или домен, не
совпавший с `BASE_URL`, останавливают выкат, а не всплывают потом молчанием
бота.

### Подписка сервиса

**Деньги бот уже принимает, но подписка пока никого не отключает.** Механизм
собран целиком: срок считается, продления пишутся в журнал, оплата звёздами
работает, гейты и напоминания проверены тестами. Но `SUBSCRIPTION_ENFORCED` по
умолчанию выключен, и в этом состоянии бот работает так, будто подписки нет
вовсе — ни один сервис не пропадёт из поиска, ни одно письмо не уйдёт, пробный
период ничем не кончится.

Включается одной строкой в день, когда решено включать:

    SUBSCRIPTION_ENFORCED=true

С этого момента работает всё: сервис без оплаченного срока пропадает из поиска,
ссылка на него ведёт к телефону, форма не отдаётся и заявка не принимается.
Кабинет управляющего при этом остаётся открытым — иначе ему нечем было бы
заплатить, — а уже записанные клиенты приходят в своё время.

Продлевает владелец бота командой `/extend <id сервиса> <дней>`; кому она
доступна, задаёт `BOT_OWNER_IDS`. Дней — от 1 до 36500; сто лет и есть
«бессрочная подписка», отдельного состояния для неё не заведено. Со знаком
минус дни отбираются обратно.

**Пробный период** — `TRIAL_DAYS` дней, и даётся он человеку, а не сервису:
второй сервис того же управляющего начинается без срока и работает только
после оплаты. Иначе бесплатная работа продлевается регистрацией нового сервиса
каждые пять дней, и подписку можно не покупать никогда; удалённые сервисы в
этой проверке тоже считаются — «удалить и завести заново» тот же обход, только
в два шага.

Пока `SUBSCRIPTION_ENFORCED` выключен, про пробный период бот молчит: называть
дату, после которой ничего не произойдёт, — обещание отключения, которого не
будет. Включите гейты — и дата появится в приветствии после регистрации, а за
сутки до конца и в день истечения придут письма.

### Чем платят

Способов два, выбирает `PAYMENT_METHOD`. Экран тарифов у них общий, разница —
в том, что появляется после нажатия на срок.

| | `stars` | `yoomoney` |
|---|---|---|
| Что получает управляющий | счёт Telegram | ссылку на форму перевода |
| Комиссия | около трети (Apple и Google) | единицы процентов |
| Кто начисляет дни | бот, сразу | бот по уведомлению ЮMoney; без `YOOMONEY_NOTIFY_SECRET` — владелец бота командой |
| Возврат | `/refund`, звёзды уходят обратно | руками в кабинете ЮMoney |
| Цены | `STARS_PRICE_1M`, `_3M`, `_12M` | `PRICE_1M`, `PRICE_3M`, `PRICE_12M` |

Управляющий платит кнопкой «💳 Подписка» в меню или кнопкой под письмом о
подписке. Обе ведут на один экран тарифов, а счёт или ссылка собираются в
момент нажатия — поэтому кнопка из старого письма не устаревает и не выставит
счёт по прошлогодней цене.

### Оплата переводом (`PAYMENT_METHOD=yoomoney`)

Нужен только номер кошелька в `YOOMONEY_WALLET` — ни ключей, ни договора.
Ссылка собирается с подставленной суммой и назначением платежа, человеку
остаётся подтвердить перевод.

Связывает деньги с сервисом метка платежа — `sub:<idservice>:<дней>`. ЮMoney
возвращает её нетронутой и в истории переводов, и в уведомлении: имя
плательщика о сервисе не говорит ничего, больше связать нечем.

**Автоматическое зачисление.** Заполните `YOOMONEY_NOTIFY_SECRET` — и дни
начисляются сами, как при оплате звёздами. Где взять секрет и куда вписать
адрес: <https://yoomoney.ru/transfer/myservices/http-notification>

| Поле на странице ЮMoney | Что вписать                           |
|-------------------------|---------------------------------------|
| Адрес для уведомлений   | `<BASE_URL>/yoomoney/notify`          |
| Секрет                  | скопировать в `YOOMONEY_NOTIFY_SECRET`|
| Отправлять уведомления  | включить                              |

Каждое уведомление подписано этим секретом, и подпись проверяется первой:
адрес публичный, и без проверки подписку продлевал бы себе любой желающий
одной строкой в `curl`. Пустой `YOOMONEY_NOTIFY_SECRET` закрывает приём
совсем — эндпоинт отвечает 404, а не «принимаю что угодно».

Что бот делает с уведомлением:

- **перевод принят, метка наша, сумма сошлась** — начисляет дни, пишет
  управляющему «оплата прошла» и владельцу бота «перевод зачислен»;
- **повторная доставка** — начисляет один раз: право на начисление занято
  уникальным индексом по `(source, external_id)`, где `external_id` —
  номер операции ЮMoney;
- **пришло меньше 90% цены тарифа** — не начисляет и зовёт владельца бота.
  Сумма стоит в адресе ссылки открытым текстом, и правится она одной рукой;
- **перевод с защитным кодом или непринятый** — не начисляет: на кошелёк он
  ещё не лёг. Когда примете — ЮMoney пришлёт уведомление заново;
- **метка не наша или сервис удалён** — не начисляет и зовёт владельца бота
  разобрать руками.

**Без секрета** всё работает, но дни начисляет владелец бота. Чтобы это не
превращалось в расследование, бот в момент выдачи ссылки пишет ему: какой
сервис, какой тариф, сколько рублей и готовую команду:

    /extend sub:11111111-1111-1111-1111-111111111111:30

Команда принимает метку целиком — делить строку руками значит однажды
ошибиться в чужом uuid.

Кошелёк не задан — экран оплаты честно скажет, что оплата недоступна, и
позовёт владельца письмом; проверка перед выкатом до этого не доводит и
останавливает выкат заранее.

### Оплата звёздами (`PAYMENT_METHOD=stars`)

Цена задаётся целым числом звёзд. Ни договора, ни `provider_token` звёзды не
требуют — бот принимает их сразу, и дни начисляются без участия человека.

Оплата удалённого сервиса его восстанавливает: деньги списаны, и оставить
человека без товара нельзя. Возвращается сам сервис — отменённые при удалении
заявки не воскресают, снятые админы не возвращаются.

Возврат делает владелец бота: `/refund <id списания>`. Звёзды возвращаются
плательщику, выданные дни отбираются, срок может уйти в прошлое — не заплатил,
не пользуешься. Идентификатор списания виден в журнале
`subscription_payments.external_id`.

Если звёзды Telegram уже отдал, а база в тот момент упала, дни отбираются
отдельной командой: `/revoke <id списания>`. Повторять `/refund` в этом случае
бесполезно — Telegram откажет, потому что платёж он уже вернул. `/revoke`
трогает только срок, звёзд не касается, работает и по удалённому сервису и
безопасен при повторе: дважды дни не вычтутся.

Все три команды — `/extend`, `/refund` и `/revoke` — доступны только тем, чьи
Telegram id перечислены в `BOT_OWNER_IDS`. **Пустое значение не пропускает
никого** — заполните переменную первым делом, иначе команды молчат и на
владельца бота.

**Напоминания бот будит сам** — раз в час, изнутри процесса
(`REMINDER_TICK_SECONDS`). Настраивать крон не нужно: разворачивание на новом
сервере не должно требовать помнить про него, а забытый крон не сообщает о
себе — гейты стоят, сроки идут, писем просто нет.

Ручной запуск рассылки остался эндпоинтом на случай отладки:

    curl -fsS -X POST -H "X-Tick-Secret: <TICK_SECRET>" \
        https://<host>/internal/subscriptions/tick

Пока `TICK_SECRET` пуст, эндпоинт закрыт совсем — на работу напоминаний это не
влияет. Пропущенные круги подписку не ломают: срок считается из `paid_until`,
рассылка только шлёт письма и помечает отправленное.

### Порядок выката подписки на живую базу

`schema.sql` применяется **до** выката кода. Наоборот нельзя: у всех сервисов
`paid_until` пуст, а пустой срок означает «не активен» — при включённом
`SUBSCRIPTION_ENFORCED` сервисы в ту же секунду пропадут из поиска и перестанут
принимать заявки.

Перед тем как поставить `SUBSCRIPTION_ENFORCED=true`, прогоните отчёт — он
покажет по именам, кто погаснет в ту же секунду, и есть ли у этих сервисов уже
записанные клиенты:

```bash
docker compose exec app python scripts/preflight_subscription.py
```

Код возврата 1 означает «включать рано»: в отчёте есть пункты `[стоп]` — сервис
с пустым сроком, пустой `BOT_OWNER_IDS` (тогда продлить не сможет никто,
включая вас) или тариф с нулевой ценой.

После выката кода прогоните `schema.sql` ещё раз. Бэкфил стоит под
`WHERE paid_until IS NULL` и повторного вреда не делает, зато подберёт
сервисы, зарегистрированные старым кодом в зазоре между двумя шагами: такой
сервис остался бы с пустым сроком, то есть просроченным, и в рассылку бы не
попал — погас бы молча.

## Как это работает

### Клиент
1. Открывает бота → видит кнопку **«Записаться в автосервис»**
2. В WebApp выбирает город → видит список сервисов → выбирает сервис
3. Заполняет форму (имя, телефон, авто, проблема, срочность)
4. Нажимает «Отправить» → данные через `tg.sendData()` попадают в бот
5. Получает подтверждение с номером заявки

### Администратор
- Получает уведомление о новой заявке с кнопками: **Принять / Позвонили / Отказать**
- При смене статуса клиент получает уведомление

### Управляющий
- Регистрирует сервис через `/register_service` (5-шаговый FSM)
- Получает **ссылку** (`https://t.me/bot?start=SVC_<uuid>`) для размещения
- Управляет администраторами через **«➕ Добавить»** / **«➖ Удалить»**

### Deep-link
Клиент открывает бота по ссылке `?start=SVC_<uuid>` → сразу видит форму записи конкретного сервиса (WebApp открывается с `?service_id=<uuid>`).

## Мягкое удаление

Ни одна запись физически не удаляется. Используется поле `idrecstatus`:

| Значение | Смысл |
|---|---|
| `0` | Активная запись |
| `-1` | Удалена / неактивна |

Для восстановления достаточно выполнить:
```sql
UPDATE admins SET idrecstatus = 0 WHERE idusertg = 123456789;
```

## Локальный запуск

```bash
# 1. Клонировать / скопировать файлы
cd autoservice_bot

# 2. Создать виртуальное окружение
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Создать .env из примера
cp .env.example .env
# Заполнить .env своими значениями

# 5. Применить схему к своей базе
psql "$DATABASE_URL" -f schema.sql

# 6. Запустить: бот, API и форма записи — один процесс
uvicorn app:app --host 127.0.0.1 --port 8080
```

Без `BASE_URL` вебхук не ставится и апдейтов бот не получает — для отладки
самого API это нормально, а чтобы поговорить с ботом, нужен публичный HTTPS
(`ngrok http 8080` и его адрес в `BASE_URL`).

То же самое в контейнере, ближе к бою:

```bash
docker compose up --build
```

## Резервные копии

Снимки базы делает сервис `backup` из `docker-compose.yml` — он поднимается
вместе с ботом по `docker compose up -d`, настраивать ничего не нужно. Раз в
`BACKUP_INTERVAL_HOURS` он кладёт в `./backups` файл
`autoservice-YYYYMMDD-HHMMSS.dump` и удаляет всё старше последних `BACKUP_KEEP`
штук. Если снимок не получился, владельцу бота приходит сообщение в Telegram:
молчащий бэкап хуже отсутствующего.

Снимок вне очереди:

```bash
docker compose run --rm --entrypoint /bin/sh backup /usr/local/bin/backup_db.sh
```

Восстановление — `import_dump.sh`. Он спросит подтверждение, сам снимет копию
того, что затрёт, зальёт дамп и догонит схему до текущей версии:

```bash
docker compose stop app
./scripts/import_dump.sh backups/autoservice-20260830-030000.dump
docker compose start app
```

### Вывоз копий с машины

Папка `./backups` лежит на том же диске, что и бот: она спасает от ошибочного
`DELETE` и неудачной миграции, но не от потери сервера — он унесёт базу и копии
разом. Увозит их сервис `offsite`: раз в час он копирует снимки туда, куда
указывает `BACKUP_REMOTE`, удаляет в хранилище всё старше `BACKUP_KEEP`
снимков и проверяет, что свежий снимок там действительно есть. Не уехали —
владельцу бота приходит сообщение в Telegram, и приходит один раз, а не каждый
час; когда вывоз восстановится, придёт и об этом.

Хранилище настраивается один раз — это единственный шаг, который нельзя
сделать за вас: у бота нет вашей учётной записи. На сервере, в каталоге
проекта:

```bash
mkdir -p secrets
docker run --rm -it -v "$PWD/secrets:/config/rclone" rclone/rclone:1 config
```

`rclone` проведёт по вопросам и запишет `secrets/rclone.conf` (каталог в
`.gitignore` — в нём пароли и токены открытым текстом). Имя, которое вы
дадите хранилищу, впишите в `.env` и выкатите:

```bash
BACKUP_REMOTE=yadisk:autoservice-backups
```

Годится всё, что умеет `rclone`: Яндекс.Диск, S3, WebDAV, SFTP на вашу
домашнюю машину. Если хранилище чужое, а в базе персональные данные клиентов,
заводите поверх него `crypt`-хранилище — тогда наружу уедут зашифрованные
файлы, а ключ останется у вас.

Что уехало:

```bash
docker compose exec offsite rclone --config /config/rclone/rclone.conf \
    lsl "$BACKUP_REMOTE"
```

Забрать оттуда снимок для восстановления — тот же `rclone copy` в обратную
сторону, дальше обычный `import_dump.sh`.

**Переезд с внешней базы.** Тем же сервисом снимается дамп чужой базы, тем же
скриптом заливается в свою:

```bash
docker compose run --rm -e BACKUP_DATABASE_URL="postgresql://...supabase.com:5432/postgres"   --entrypoint /bin/sh backup /usr/local/bin/backup_db.sh
./scripts/import_dump.sh backups/autoservice-<дата>.dump
nano .env            # DATABASE_URL → postgresql://autoservice:<пароль>@db:5432/autoservice?sslmode=disable
./scripts/deploy.sh
```

Бота на время переезда лучше остановить (`docker compose stop app`): заявка,
пришедшая между снимком и заливкой, останется в старой базе.

## Эксплуатация

**За обратным прокси.** На VPS перед ботом обычно стоит Caddy или nginx — он
держит HTTPS, а `uvicorn` слушает localhost. В этом случае поставьте
`TRUST_PROXY=true`: иначе все запросы придут с адреса прокси, попадут в один
счётчик, и первый же активный клиент исчерпает лимит частоты для всех
остальных. Без прокси оставьте `false` — тогда `X-Forwarded-For` пишет сам
клиент, и доверять ему значит не иметь лимита вовсе.

**Перезапуск.** Вебхук ставится с `drop_pending_updates=True`: накопленные за
время простоя апдейты Telegram выбрасывает. Так задумано — после долгой
остановки бот не отвечает пачкой на сообщения получасовой давности. Цена:
нажатия кнопок, сделанные при выключенном боте, пропадают молча.

**Возврат звёзд.** `/refund` работает, пока Telegram держит звёзды у себя;
после вывода средств он в возврате откажет — тогда останется `/revoke`, который
отбирает дни, не трогая деньги. Срок удержания задаёт Telegram (сейчас порядка
трёх недель), поэтому спорные платежи разбирайте, не откладывая.

**Личные данные.** `PII_RETENTION_DAYS` — через сколько дней после закрытия
заявки затираются имя, телефон и комментарий клиента. По умолчанию `0`: уборка
выключена, срок хранения выбирает владелец сервиса. Время, услуги и статус
остаются в любом случае — отчётность не страдает. Клиент может стереть свои
данные сам командой `/forget_me`; пока у него есть незакрытые заявки, команда
отказывает — сервису надо к кому-то приехать.

## Тесты

```bash
.venv/Scripts/python.exe -m pytest -q      # Windows
.venv/bin/python -m pytest -q              # Linux / macOS
```

Часть тестов работает с настоящей базой: создаёт сервисы, заявки и подписки, а
после себя удаляет их. Поэтому у сюиты должна быть **своя** база, отдельная от
боевой — иначе однажды прогон снесёт живые данные:

```bash
# на машине разработчика — свой PostgreSQL
createdb autoservice_test
psql autoservice_test -f schema.sql

# в .env
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/autoservice_test
```

На сервере то же самое делается второй базой в том же контейнере:

```bash
docker compose exec db createdb -U autoservice autoservice_test
docker compose exec -T db psql -U autoservice -d autoservice_test -q < schema.sql
```

Без `TEST_DATABASE_URL` тесты идут в `DATABASE_URL` и на каждом прогоне пишут об
этом предупреждение. Полный прогон против удалённой базы занимает 12–15 минут;
локальная база проходит его за минуты.
