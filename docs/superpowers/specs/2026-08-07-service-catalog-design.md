# Справочник услуг сервиса — дизайн

Дата: 2026-08-07

## Задача

Список услуг («Диагностика», «Ремонт двигателя», …) сейчас жёстко зашит в
`config.SERVICE_TYPES` и продублирован в `webapp/index.html`. Он одинаков для
всех автосервисов, а профиль работ у них разный: детейлинг-студии не нужны
восемь из девяти стандартных услуг.

Управляющий должен сам добавлять и удалять услуги своего сервиса.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Чей список | Свой у каждого сервиса. При регистрации копируются 9 шаблонных услуг |
| Удаление | Мягкое (`idrecstatus = -1`) — история заявок и статистика не ломаются |
| Права | Только управляющий (owner). У администраторов кнопки нет |
| Где редактировать | В боте. WebApp остаётся клиентской формой записи |
| Пустой список | Запрещён: минимум одна услуга должна остаться |
| Лимиты | До 30 услуг на сервис, название 2–40 символов, дубликаты запрещены |

## Архитектура

Отдельная таблица `service_catalog` + ссылка из заявки + снимок названия
в самой заявке.

Снимок названия (`requests.service_title`) — ключевое решение. Оно позволяет
карточке заявки и статистике работать без JOIN'ов: `render.py` и запросы в
`database.py` почти не меняются. Альтернатива — читать название через JOIN —
потребовала бы переписать все SELECT'ы вокруг заявок ради устранения одного
дублирующегося поля. Хранение списка в JSONB-колонке `services` отвергнуто:
у услуги не было бы стабильного идентификатора, а цена и длительность —
вероятное следующее пожелание — превратились бы в миграцию формата.

## Схема данных

```sql
CREATE TABLE IF NOT EXISTS service_catalog (
    idcatalog   uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    idservice   uuid        NOT NULL REFERENCES services(idservice) ON DELETE CASCADE,
    title       text        NOT NULL,
    sort_order  int         NOT NULL DEFAULT 100,
    idrecstatus smallint    NOT NULL DEFAULT 0,
    createdate  timestamptz NOT NULL DEFAULT now(),
    deletedate  timestamptz
);

CREATE INDEX IF NOT EXISTS idx_catalog_service
    ON service_catalog (idservice) WHERE idrecstatus = 0;

-- в одном сервисе не может быть двух активных услуг с одинаковым названием
CREATE UNIQUE INDEX IF NOT EXISTS idx_catalog_unique_title
    ON service_catalog (idservice, lower(trim(title))) WHERE idrecstatus = 0;

ALTER TABLE requests
    ADD COLUMN IF NOT EXISTS idcatalog     uuid REFERENCES service_catalog(idcatalog) ON DELETE SET NULL,
    ADD COLUMN IF NOT EXISTS service_title text NOT NULL DEFAULT '';

CREATE INDEX IF NOT EXISTS idx_requests_catalog ON requests (idcatalog);

ALTER TABLE service_catalog ENABLE ROW LEVEL SECURITY;
```

### Бэкфил

Живёт в том же `schema.sql`, идемпотентен — файл рассчитан на повторный прогон.

1. Каждому активному сервису с пустым каталогом вставляются 9 шаблонных услуг
   с `sort_order` по порядку следования.
2. Существующим заявкам проставляются `service_title` и `idcatalog` по
   соответствию ключ→название (`engine` → «Ремонт двигателя» и т.д.), заданному
   списком `VALUES` прямо в SQL.

Колонка `requests.service_type` остаётся в схеме. Приложение её не читает и не
пишет (срабатывает дефолт `'other'`). Удаление колонки — отдельный шаг после
того, как бэкфил подтвердится на боевых данных: иначе откатываться будет не к чему.

## Изменения по файлам

### `config.py`

`SERVICE_TYPES: dict[str, str]` → `DEFAULT_SERVICE_TITLES: tuple[str, ...]` —
кортеж из 9 названий. Слаги-ключи больше не нужны нигде, кроме бэкфила,
а он живёт в SQL.

### `database.py` — блок `# ── service_catalog ──`

- `seed_catalog(conn, idservice)` — вставляет `DEFAULT_SERVICE_TITLES`.
  Вызывается внутри существующей `create_service()` в той же транзакции:
  сервис без услуг не должен существовать даже на миллисекунду.
- `get_catalog(idservice)` — активные услуги, `ORDER BY sort_order, title`.
- `get_catalog_item(idservice, idcatalog)` — одна активная услуга. Фильтр по
  `idservice` обязателен: он не даёт клиенту прислать `idcatalog` чужого сервиса.
- `add_catalog_item(idservice, title)` — вставка. Ранее удалённая услуга с тем
  же названием **воскрешается** (`idrecstatus = 0`), а не создаётся заново:
  старые заявки снова оказываются слинкованы со своей услугой. При конфликте
  с активной услугой возвращает `None`.
- `delete_catalog_item(idservice, idcatalog)` — мягкое удаление одним условным
  UPDATE:

```sql
UPDATE service_catalog SET idrecstatus = -1, deletedate = now()
WHERE idcatalog = $1 AND idservice = $2 AND idrecstatus = 0
  AND (SELECT count(*) FROM service_catalog
        WHERE idservice = $2 AND idrecstatus = 0) > 1
RETURNING *
```

  Правило «хотя бы одна услуга» живёт в запросе, а не в хендлере: иначе
  управляющий с двух устройств удалит две последние услуги одновременно,
  обе проверки пройдут, и сервис останется пустым. Тот же приём с условным
  UPDATE уже применён в `update_request_status`.

- `count_requests_by_catalog(idservice, idcatalog)` — для текста подтверждения.
- `get_service_type_breakdown()` — `GROUP BY service_type` → `GROUP BY service_title`.
- `create_request()` — вместо `service_type` пишет `idcatalog` и `service_title`.

### `validators.py`

- `validate_service_type()` удаляется: проверить услугу без обращения к базе
  больше нельзя.
- `validate_service_title(raw)` — очистка + длина 2–40 символов, для ввода
  управляющего.
- `validate_request_fields()` больше не отвечает за услугу.

### `handlers/requests.py`

Проверка выбранной клиентом услуги переезжает в `create_request_flow()`, рядом
с уже существующими проверками сервиса, кулдауна и лимита заявок:
`db.get_catalog_item(...)` → при пустом результате `RequestRejected("Эта услуга
больше не оказывается — выберите другую")`.

Legacy-хендлер `web_app_data` остаётся, но заявки со старым полем `service_type`
отклоняются с текстом «Форма записи устарела — закройте её и откройте заново».
Маппинг старых ключей не делаем: бот не в проде, закешированных старых форм ни
у кого нет, а код за такой маппинг пришлось бы платить навсегда.

### `handlers/catalog.py` — новый файл (~150 строк)

Отдельно от `admin_mgmt.py`: тот уже 286 строк и отвечает за людей, а не за услуги.
Роутер регистрируется в `app.py` рядом с `admin_mgmt`.

Экран по кнопке `🔧 Услуги`:

```
🔧 Услуги — «Автосервис на Ленина»

1. Диагностика
2. Замена масла
3. Шины и диски
...

Всего 9 из 30. Нажмите на услугу, чтобы удалить.
```

Inline-клавиатура: по кнопке на услугу (`❌ Диагностика`, callback
`svcdel:<idcatalog>`), последней строкой `➕ Добавить услугу` (callback `svcadd`).

**Удаление:** тап → сообщение редактируется в подтверждение через существующий
`kb_confirm("svcdelok", idcatalog)`:

> Удалить услугу «Ремонт двигателя»?
> По ней уже 3 заявки — они останутся в истории и статистике.
> Клиенты больше не смогут выбрать её при записи.

Подтверждение → удаление → сообщение снова становится списком услуг.
Если услуга последняя, `delete_catalog_item` вернёт `None` → алерт
«Нельзя удалить последнюю услугу — сначала добавьте другую».

**Добавление:** FSM `ServiceCatalog.title` (по образцу `RegService` из
`register.py`) → приглашение ввести название с `kb_cancel()` → валидация →
вставка → обновлённый список и возврат в главное меню. Ошибки («уже есть такая»,
«лимит 30 услуг», «2–40 символов») выводятся текстом с сохранением состояния FSM.

Каждый хендлер начинается с `require_active_service()` и проверки `owner_id`,
включая callback'и: без проверки в callback'е администратор мог бы подобрать
`idcatalog` и удалить услугу. Та же защита стоит в `remove_admin_confirm`.

### `keyboards.py`

`BTN_SERVICES = "🔧 Услуги"`, отдельной строкой в `kb_owner_main()` перед
кнопкой записи. В `kb_admin_main()` кнопки нет.

### `app.py`

`GET /api/service/{service_id}` отдаёт дополнительное поле:

```json
{ "idservice": "...", "service_name": "...", "service_number": "...",
  "city": "...", "location_service": "...",
  "catalog": [ { "idcatalog": "...", "title": "Диагностика" } ] }
```

Отдельный эндпоинт не нужен: форма и так дёргает этот, а услуг максимум 30.
`GET /api/services?city=` не меняется — в списке сервисов по городу услуги
не показываются.

В `RequestPayload` поле `service_type: str` заменяется на `idcatalog: str`.

### `render.py`

`service_type_label()` удаляется. Везде, где стоял
`service_type_label(req['service_type'])`, подставляется `req['service_title']`.
JOIN'ов не добавляется.

### `webapp/index.html`

Захардкоженный массив `SERVICE_TYPES` удаляется целиком.

Сейчас есть развилка: при заходе по deep-link'у форма запрашивает
`/api/service/{id}`, а при поиске по городу берёт объект из результатов поиска
и никуда не ходит — во второй ветке услуг взять неоткуда. Обе ветки сводятся
к одной: выбрали сервис → спиннер → `/api/service/{id}` → форма. Заодно
исчезает дубль логики отрисовки.

Селект «Тип работы» строится из `catalog`, значение опции — `idcatalog`.
В теле POST `/api/requests` поле `service_type` заменяется на `idcatalog`.

## Граничные случаи

| Ситуация | Поведение |
|---|---|
| Удаляют последнюю услугу | Условный UPDATE не срабатывает → алерт «Нельзя удалить последнюю» |
| Два окна бота удаляют предпоследнюю и последнюю одновременно | Второй UPDATE не проходит, одна услуга остаётся |
| Клиент открыл форму, управляющий удалил услугу, клиент отправил | `RequestRejected`: «Эта услуга больше не оказывается — выберите другую» |
| Добавляют услугу, которая уже есть | «Такая услуга уже есть в списке», состояние FSM сохраняется |
| Добавляют услугу, которую раньше удалили | Строка воскресает, старые заявки снова слинкованы |
| Клиент прислал `idcatalog` чужого сервиса | `get_catalog_item` фильтрует по `idservice` → отказ |
| Администратор жмёт подобранный callback `svcdel:` | Проверка `owner_id` в callback-хендлере → алерт |
| Сервис из старой базы без каталога | Бэкфил в `schema.sql` создаёт 9 услуг при первом прогоне |

## Проверка

Тестов в проекте нет. Разворачивать полноценную инфраструктуру ради одной фичи —
перебор, поэтому минимум, который ловит ошибки именно здесь:

- `pytest` + `pytest-asyncio` в `requirements.txt`, каталог `tests/`.
- `tests/test_catalog.py` — слой БД против базы из `DATABASE_URL` (файл целиком
  пропускается, если переменная не задана). Каждый тест создаёт временный сервис
  и удаляет его за собой. Покрываем: сид 9 услуг при регистрации, запрет удаления
  последней, воскрешение удалённой, отказ на дубликат, `get_catalog_item` не
  отдаёт чужую услугу.
- `tests/test_validators.py` — `validate_service_title`: обрезка пробелов,
  границы 2 и 40 символов, управляющие символы.

Ручной чек-лист (бот и WebApp автотестами не покрываем — не окупается):
зарегистрировать сервис → увидеть 9 услуг → удалить 8 → убедиться, что девятая
не удаляется → добавить «Полировка» → открыть форму записи и увидеть в селекте
ровно две услуги → отправить заявку → проверить, что в карточке администратору
и в статистике стоит «Полировка».

## Вне области

- Переименование услуг и изменение порядка (`sort_order` заполняется, но UI нет).
- Цена и длительность услуги.
- Редактирование услуг из WebApp.
- Удаление колонки `requests.service_type` — отдельным шагом после проверки бэкфила.
