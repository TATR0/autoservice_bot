# Несколько услуг в заявке и цена услуги — дизайн

Дата: 2026-08-12

## Задача

Заявка сегодня содержит ровно одну услугу. В жизни клиент приезжает сразу за
несколькими работами: полировка кузова, полировка фар, химчистка салона. Ему
приходится либо слать три заявки, либо перечислять остальное в комментарии — и
тогда это не попадает ни в карточку администратору, ни в статистику.

Заодно каталог получает цену: сейчас клиент не знает, сколько будет стоить, и
звонит именно за этим.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Цена обязательна? | Нет. Не указана — клиент видит «цена по запросу» |
| Точная или «от»? | Всегда «от N ₽». Отдельного флага нет |
| Длительность услуги | Не делаем. Появится вместе с расписанием, где заработает |
| Снимок в заявке | Да: название и цена сохраняются такими, какими их видел клиент |
| Услугу удалили, пока клиент заполнял | Заявка отклоняется целиком, с названием услуги |
| Сколько услуг в заявке | Минимум одна, верхнего предела нет (в каталоге максимум 30) |

## Что сознательно вне области

- **Расписание и запись на время** — отдельная подсистема со своей спекой:
  шаблон рабочих часов, выходные, число постов, занятость слотов, перенос.
  Именно потому, что расписание будет строиться на часовых слотах, а не на
  длительности работ, длительность услуги здесь не нужна.
- **Поле «срочность»** остаётся как есть. Оно потеряет смысл, когда появится
  выбор времени, и уберём мы его тогда же.
- Переименование услуг и ручная сортировка.

## Архитектура

Позиции заявки живут в отдельной таблице `request_services`: одна строка на
одну выбранную услугу.

Альтернативы отвергнуты. JSONB-массив в `requests` лишает позицию стабильного
идентификатора, превращает статистику в разбор JSON и держит связь с каталогом
на честном слове вместо внешнего ключа — те же грабли, из-за которых каталог
услуг в прошлой фиче не стали хранить в JSONB. Схема «одна главная услуга плюс
остальные списком» вводит понятие «главной услуги», которого в предметной
области не существует.

## Схема данных

```sql
ALTER TABLE service_catalog
    ADD COLUMN IF NOT EXISTS price_rub int;

ALTER TABLE service_catalog DROP CONSTRAINT IF EXISTS chk_catalog_price;
ALTER TABLE service_catalog ADD  CONSTRAINT chk_catalog_price
    CHECK (price_rub IS NULL OR price_rub BETWEEN 0 AND 10000000);

CREATE TABLE IF NOT EXISTS request_services (
    idrequestservice uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    idrequests       uuid        NOT NULL REFERENCES requests(idrequests) ON DELETE CASCADE,
    idcatalog        uuid        REFERENCES service_catalog(idcatalog) ON DELETE SET NULL,
    title            text        NOT NULL,
    price_rub        int,
    position         int         NOT NULL DEFAULT 0,
    createdate       timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_request_services_request
    ON request_services (idrequests);
CREATE INDEX IF NOT EXISTS idx_request_services_catalog
    ON request_services (idcatalog);

-- одну и ту же услугу нельзя добавить в заявку дважды
CREATE UNIQUE INDEX IF NOT EXISTS idx_request_services_unique
    ON request_services (idrequests, idcatalog) WHERE idcatalog IS NOT NULL;

ALTER TABLE request_services ENABLE ROW LEVEL SECURITY;
```

Цена — целое число рублей: копейки в прайсе автосервиса не встречаются, а
`numeric` тянет округления на ровном месте. `NULL` означает «не указана» и
отличается от нуля, который значил бы «бесплатно».

`title` и `price_rub` в `request_services` — снимки на момент оформления.
`position` хранит порядок, в котором клиент видел услуги, чтобы карточка
администратору совпадала с формой.

### Миграция

Бэкфил переносит существующие заявки: у каждой сегодня ровно одна услуга, она
становится позицией с `position = 0`. Идемпотентно, как прежние миграции.

```sql
INSERT INTO request_services (idrequests, idcatalog, title, position)
SELECT r.idrequests, r.idcatalog, r.service_title, 0
  FROM requests r
 WHERE r.service_title <> ''
   AND NOT EXISTS (
        SELECT 1 FROM request_services rs WHERE rs.idrequests = r.idrequests);
```

Заодно платим старый долг: колонка `requests.service_type` удаляется — она
мертва с прошлой фичи, её бэкфил отработал и проверен. Колонки
`requests.idcatalog` и `requests.service_title` становятся legacy на один
релиз: код их не читает, данные остаются на случай отката.

## Слой БД

**Каталог:**

- `add_catalog_item(idservice, title, price_rub=None)` — параметр со значением
  по умолчанию, существующие вызовы и тесты не ломаются.
- `set_catalog_item_price(idservice, idcatalog, price_rub)` — правка цены
  заведённой услуги. Отдельный метод, а не «обновить всё»: переименование
  услуг вне области, смешивать операции незачем.
- `get_catalog_items(idservice, idcatalogs, *, only_active=True)` — читает
  пачку услуг по списку идентификаторов одним запросом. Фильтр по `idservice`
  обязателен: он не даёт подставить услугу чужого сервиса. Флаг
  `only_active=False` нужен, чтобы назвать удалённую услугу по имени в тексте
  отказа, а не отделаться безличным «одна из услуг недоступна».

**Заявка:**

- `create_request(..., services: list[dict])` — вместо пары `idcatalog` и
  `service_title` принимает список позиций. Каждая позиция — словарь с ключами
  `idcatalog: str`, `title: str`, `price_rub: int | None`; `position`
  проставляется по порядку элементов списка, вызывающему считать его не нужно.
  Заявка и её строки пишутся в одной транзакции: заявки без услуг существовать
  не должно даже мгновение. Legacy-колонки `idcatalog` и `service_title` в
  `requests` при вставке не заполняются — срабатывают дефолты.
- `get_request_services(idrequests)` — позиции по `position`.
- `get_service_breakdown()` переезжает на `request_services`. Это чинит
  существующее искажение: сегодня заявка с тремя работами попадает в
  статистику как одна.
- `count_requests_by_catalog()` считает по `request_services`.

**Суммы нигде не хранятся** — ни в заявке, ни в позициях. Складываются при
отображении. Хранить итог значило бы держать второй источник правды, который
разъедется при первой же правке позиции.

## Интерфейс управляющего

Тап по услуге открывает карточку, а не сразу удаление:

```
🔧 Полировка кузова

💰 Цена: от 3 000 ₽

[💰 Изменить цену]  [❌ Удалить услугу]
[⬅️ К списку]
```

Список показывает цены, чтобы не открывать каждую:

```
🔧 Услуги — «Автосервис на Ленина»

1. Полировка кузова — от 3 000 ₽
2. Полировка фар — от 1 500 ₽
3. Химчистка салона — цена по запросу
```

**Добавление услуги** — два шага: название, затем цена. На шаге цены работает
ответ `-`, приглашение об этом прямо говорит. Отдельного вопроса «указывать
цену или нет» не будет: лишний тап на каждой из тридцати услуг дороже одной
понятной подсказки.

**Правка цены** — та же логика, `-` очищает уже заданное значение.

Технически это два независимых потока FSM: один добавляет услугу целиком,
второй правит цену существующей. Смешивать их в один с флагами не стоит —
каждый читается сверху вниз.

Форматирование живёт в `render.py`: `price_label` даёт «от 3 000 ₽» или
«цена по запросу». Одно место на бота и форму, иначе разъедется.

Права не меняются: каталог правит только управляющий.

## Форма записи

Селект заменяется списком с галочками — он читается как прайс-лист, а именно
за этим клиент открывает форму:

```
Услуги *
☑ Полировка кузова        от 3 000 ₽
☐ Полировка фар           от 1 500 ₽
☐ Химчистка салона        цена по запросу

Итого: от 3 000 ₽
```

Итог пересчитывается при каждом переключении галочки. Складываются только
указанные цены; если среди выбранного есть работы без цены, под итогом
появляется «часть работ — по запросу», чтобы сумма не выглядела полной.

Родной `<select multiple>` не берём: на телефоне это крошечный список с
невнятным выделением.

**В теле запроса уезжает только список идентификаторов** — `idcatalogs`. Цены
форма не отправляет: сервер берёт их из своей базы и сам кладёт в снимок.
Иначе подменённый запрос записал бы «полировка кузова, 1 рубль», и
администратор увидел бы это как обещание сервиса. Сумма на экране — только для
показа.

`GET /api/service/{id}` отдаёт в каталоге дополнительное поле `price_rub`.

## Граничные случаи

| Ситуация | Поведение |
|---|---|
| Не выбрано ни одной услуги | Форма не отправляется, ошибка рядом со списком. Сервер проверяет то же самое — на клиента не полагаемся |
| Услугу удалили, пока клиент заполнял | Отказ с названием: «Услуга „Полировка фар“ больше не оказывается» |
| Прислан `idcatalog` чужого сервиса | Отклоняется: `get_catalog_items` фильтрует по `idservice` |
| В списке пришли дубликаты | Схлопываются до уникальных, уникальный индекс — страховка |
| Цену изменили после оформления | В заявке остаётся снимок |
| Услугу удалили после оформления | Позиция остаётся, ссылка обнуляется, название и цена живут в снимке |
| Ни у одной выбранной услуги нет цены | Итог не показывается, вместо него «цена по запросу» |
| Цена введена не числом | «Введите число рублей или «-», чтобы не указывать» |
| Отрицательная или абсурдная цена | Валидатор допускает 0 … 10 000 000 ₽ |
| Заявки до миграции | Бэкфил переносит их единственную услугу в позиции |

## Проверка

Автотестами покрываем то, где ошибка молчалива:

- `validate_price` — числа, пробелы внутри («3 000»), `-`, мусор, границы;
- позиции заявки — создание с тремя услугами разом, порядок сохраняется;
- снимок цены переживает изменение цены в каталоге и удаление самой услуги;
- отказ через `create_request_flow` на удалённой и на чужой услуге — это
  защита от подмены, её должен проверять тест, а не только глаз;
- статистика — заявка с тремя услугами даёт три позиции в разбивке.

Ручной чек-лист: завести услугу с ценой и без, поправить цену, увидеть обе в
форме, выбрать две, сверить итог, отправить, увидеть в карточке администратору
обе позиции с ценами, затем поднять цену в каталоге и убедиться, что в уже
созданной заявке она прежняя.
