# Запись на время: расписание сервиса и календарь в форме — дизайн

Дата: 2026-08-15

## Задача

Клиент сейчас выбирает «срочность» — «обычный, 7+ дней» или «срочный, сегодня».
Это не запись, а пожелание: администратор всё равно звонит и договаривается о
времени голосом. Сервис не знает своей загрузки, клиент не знает, когда его
ждут, и оба тратят звонок на то, что должно решаться в форме.

Управляющий задаёт рабочее расписание, из него нарезаются окна записи, клиент
выбирает день и время. Занятое время клиенту не показывается.

Поле «срочность» уходит: выбрав конкретный час, клиент уже сказал всё, что оно
пыталось выразить. Предыдущая спека (`2026-08-12-multi-service-request-design.md`)
оставила его именно до этого момента.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Как управляющий задаёт время | Шаблоном рабочего дня, не слотами вручную |
| Что в шаблоне | Часы, шаг, обед, рабочие дни, горизонт, машин за раз |
| Слоты хранятся в базе? | Нет. Вычисляются из шаблона, занятость берётся из заявок |
| Сколько машин в одно время | Число в шаблоне, задаёт управляющий. Сущности «пост» нет |
| Занятое время в списке | Не показывается вовсе |
| Отмена и отказ | Освобождают время сразу |
| Выполненная заявка | Держит время навсегда, это история |
| Точечно закрыть одно окно | Не в этой итерации |
| Сервис без расписания | Не бывает: строка заводится при регистрации, существующим — бэкфил |
| Часовой пояс | Зона сервиса (`services.timezone`), клиенту подписываем явно |
| Колонка `urgency` | Приложение перестаёт её использовать, удаляется отдельным коммитом |

## Что сознательно вне области

- **Точечные исключения в расписании** («в этот четверг с 14 закрыто»). Это
  отдельная таблица и отдельный экран. Обед — единственное регулярное
  исключение, и он попал в шаблон именно потому, что регулярный.
- **Длительность услуги.** Прошлая спека предполагала, что она появится вместе
  с расписанием. Не появляется: слоты фиксированного шага, и запись на два
  часа делается выбором шага 120, а не суммой длительностей. Складывать
  длительности значило бы получать окна произвольной ширины, которые не лягут
  в сетку календаря.
- **Перенос записи** клиентом или администратором. Сейчас — отмена и новая
  заявка.
- **Напоминания** за день до визита.
- **Предупреждение управляющему**, что сужение часов оставило принятые заявки
  вне расписания.

## Архитектура

Слоты нигде не хранятся. Есть шаблон (`service_schedule`, строка на сервис) и
факт занятости (`requests.scheduled_at`). Свободные окна — разность между тем,
что нарезает шаблон, и тем, что уже занято.

Альтернатива с материализацией слотов в таблицу отвергнута. Она требует
предгенерации на горизонт вперёд, а значит планировщика, которого в проекте
нет; при правке шаблона — пересоздания будущих слотов с оглядкой на занятые;
при отмене заявки — возврата счётчика. Три обязанности не забыть, три места,
где данные разъезжаются.

В выбранной схеме освобождение времени при отмене не реализовано вообще —
отменённая заявка просто перестаёт попадать в подсчёт занятости. Логики, которая
могла бы сломаться, не существует.

Нарезка живёт в новом модуле `slots.py` чистой функцией: принимает шаблон,
зону, текущий момент и занятость — возвращает свободные окна. Без базы, без
сети, без времени «сейчас» из системных часов. Это делает основную массу
поведения проверяемой обычными тестами.

## Схема данных

```sql
CREATE TABLE IF NOT EXISTS service_schedule (
    idservice    uuid        PRIMARY KEY REFERENCES services(idservice) ON DELETE CASCADE,
    work_from    time        NOT NULL DEFAULT '09:00',
    work_to      time        NOT NULL DEFAULT '18:00',
    slot_minutes int         NOT NULL DEFAULT 60,
    lunch_from   time,
    lunch_to     time,
    weekdays     smallint[]  NOT NULL DEFAULT '{1,2,3,4,5}',  -- ISO: 1=пн … 7=вс
    horizon_days int         NOT NULL DEFAULT 14,
    capacity     int         NOT NULL DEFAULT 1,
    updatedate   timestamptz NOT NULL DEFAULT now()
);
```

Ограничения:

```sql
chk_schedule_hours     work_from < work_to
chk_schedule_step      slot_minutes IN (30, 60, 90, 120)
chk_schedule_lunch     обе границы NULL, либо обе заданы,
                       lunch_from < lunch_to, обед внутри рабочих часов
chk_schedule_horizon   horizon_days BETWEEN 1 AND 60
chk_schedule_capacity  capacity BETWEEN 1 AND 20
chk_schedule_weekdays  массив непустой и вложен в {1..7}
```

Время — тип `time`, без даты и без зоны: смысл ему даёт `services.timezone`.
Хранить зону второй раз значит однажды получить две разные.

Хранятся **рабочие** дни, а не выходные. Пустой список выходных двусмыслен —
то ли работаем всю неделю, то ли поле не заполнили; пустой список рабочих дней
запрещён констрейнтом и такого вопроса не создаёт.

```sql
ALTER TABLE requests ADD COLUMN IF NOT EXISTS scheduled_at timestamptz;

CREATE INDEX IF NOT EXISTS idx_requests_scheduled
    ON requests (idservice, scheduled_at) WHERE scheduled_at IS NOT NULL;
```

Колонка nullable: у трёх существующих заявок времени нет и выдумать его нельзя.
Обязательность для новых заявок обеспечивает приложение. В карточке строка
времени не выводится, если его нет, — по тому же правилу, что принято для цен.

**Живой** заявкой, держащей время, считается заявка со `idrecstatus = 0` и
статусом из `new`, `accepted`, `called`, `in_progress`, `done`. Освобождают
время `rejected`, `cancelled`, `service_closed` и мягкое удаление.

### Миграция

Строка расписания заводится при регистрации сервиса, со значениями по
умолчанию. Существующим сервисам — бэкфил в `schema.sql`:

```sql
INSERT INTO service_schedule (idservice) SELECT idservice FROM services
ON CONFLICT (idservice) DO NOTHING;
```

Так после выката ни один сервис не оказывается «без расписания». Обратная
альтернатива — считать отсутствие строки нормальным состоянием — означала бы,
что все живые сервисы перестают принимать заявки, пока управляющий не дойдёт
до настроек.

Колонка `urgency` остаётся в базе со своим `DEFAULT 'low'` и констрейнтом.
Приложение перестаёт её читать и писать; удаление — отдельным коммитом после
того, как выкат отстоится. Ровно так в этом проекте поступили с `service_type`.

## Нарезка слотов

`slots.py`, чистая функция (имя не `schedule.py`, чтобы не путалось с
`handlers/schedule.py`):

```python
def free_slots(schedule, tz, now, taken) -> dict[date, list[time]]
```

- `taken` — сколько живых заявок на каждый момент, из одного запроса к базе.
- День попадает в результат, только если в нём остались свободные окна.
- Окна нарезаются от `work_from` шагом `slot_minutes`, пока целиком помещаются
  до `work_to`.
- Окно, попавшее в обед хотя бы частично, выбрасывается.
- Дни вне `weekdays` пропускаются, горизонт — `horizon_days` от сегодня в зоне
  сервиса.
- Окно, начинающееся раньше `now`, не предлагается. Буфера «не раньше чем через
  час» нет: сервис, готовый принять через десять минут, должен иметь такую
  возможность.
- Переход на летнее время: несуществующее локальное время пропускается, для
  задвоенного берётся первое. Москва переходов не имеет, но функция работает
  для любой зоны из `services.timezone`.

## Слой БД

- `get_schedule(idservice)` — строка расписания.
- `update_schedule(idservice, **fields)` — правка полей, возвращает строку.
- `get_taken_slots(idservice, since, until)` — счётчик живых заявок по времени.
- `create_request(..., scheduled_at)` — в одной транзакции: `SELECT … FROM
  service_schedule WHERE idservice = $1 FOR UPDATE`, подсчёт занятости, вставка.

Блокировка строки расписания — то, что делает проверку и вставку неделимыми.
Без неё два одновременных клиента оба проходят проверку до того, как любой из
них вставит строку, и одно место продаётся дважды.

Уникальный индекс эту роль сыграть не может: он выражает «не больше одного», а
вместимость настраиваемая. Побочный эффект блокировки — заявки в один сервис
выстраиваются в очередь; для потока автосервиса это незаметно, а сервисы друг
друга не задевают.

Переполнение поднимает `RequestRejected` — механизм отказа с текстом клиенту
уже есть в `handlers/requests.py`, новый не нужен.

## Интерфейс управляющего

Кнопка «🗓 Расписание» в меню управляющего, рядом с «🔧 Услуги», с той же
проверкой прав: только владелец сервиса. Хендлеры — `handlers/schedule.py`.

Экран — карточка текущего расписания с inline-кнопками правки:

```
🗓 Расписание — Тест123

🕘 Часы работы:      09:00 — 18:00
⏱ Шаг записи:       60 минут
🍽 Обед:             13:00 — 14:00
📅 Рабочие дни:      пн, вт, ср, чт, пт
🚗 Машин за раз:     1
📆 Открыто вперёд:   14 дней

Свободных окон на ближайшие 14 дней: 47

[🕘 Часы]  [⏱ Шаг]
[🍽 Обед]  [📅 Дни]
[🚗 Машин] [📆 Горизонт]
```

Строка со свободными окнами считается тем же `free_slots`, что и форма, то есть
показывает ровно то, что увидит клиент. Считаются именно окна — моменты
времени, на которые ещё можно записаться, а не оставшиеся места: при
вместимости 3 окно, где занято одно место, засчитывается один раз. Это единственный способ для управляющего
немедленно заметить, что он поставил обед на весь день.

Часы, обед, машины и горизонт правятся текстовым вводом через FSM — как цена
услуги: подсказка, «❌ Отмена», разбор валидатором, понятная ошибка без потери
шага. Часы принимаются как `9-18` и как `09:00-18:00`, обед сбрасывается
символом `-`.

Шаг и рабочие дни правятся inline-кнопками: шаг — выбор из четырёх значений,
дни — семь переключателей с галочками и «Готово». Набор вариантов конечен и
известен заранее, печатать `пн,вт,ср,чт,пт` и разбирать опечатки незачем.

Валидаторы (`validators.py`, рядом с `validate_price`): диапазон времени,
вместимость, горизонт.

## Форма записи

Блок «Срочность» заменяется на «Когда приехать» в два шага.

**Календарь месяца.** Сетка пн–вс со стрелками переключения месяца. Три
состояния дня: доступен (есть свободные окна), недоступен (выходной, прошедший,
за горизонтом или всё разобрано) — приглушён и не нажимается, выбранный —
акцентная заливка. Стрелки упираются в границы: назад не раньше текущего
месяца, вперёд не дальше месяца с концом горизонта.

**Время выбранного дня** — плитками под календарём. Занятого времени в списке
нет вовсе. Обед выпадает сам, поэтому после 12:00 сразу 14:00. Под плитками —
подпись «время сервиса, Europe/Moscow»: без неё клиент из другой зоны выберет
час по-своему и приедет не тогда.

Рисуется своим кодом в стилях формы. Готовые библиотеки календарей — React, а
форма это один файл на чистом JS без сборки; тащить сборку ради сетки 7×N
несоразмерно.

**API.** `/api/service/{id}` начинает отдавать зону и свободные окна,
сгруппированные по дням в зоне сервиса:

```json
"timezone": "Europe/Moscow",
"slots": { "2026-08-15": ["09:00", "10:00", "14:00"], "2026-08-17": ["09:00"] }
```

На горизонт в 14 дней это сотня-полторы коротких строк — отдаются вместе с
карточкой сервиса, отдельного запроса на месяц не нужно. День доступен ровно
тогда, когда для него есть непустой список.

`POST /api/requests` принимает `scheduled_at` в виде `"2026-08-15 10:00"` —
времени сервиса, симметрично тому, что отдал `slots`. Сервер трактует его в
зоне сервиса. Поле `urgency` из payload уходит.

Форма — удобство, а не защита: сервер отдельно проверяет, что присланный момент
принадлежит расписанию и не в прошлом, потому что payload можно отправить в
обход формы.

## Граничные случаи

| Случай | Поведение |
|---|---|
| Окно заняли, пока клиент заполнял форму | Отказ «это время только что заняли», список окон обновляется |
| Два клиента жмут «Отправить» на одно окно | Блокировка расписания: первый получает заявку, второй — отказ |
| Повторный тап «Отправить» | Уникальный `client_uid`: та же заявка, второе место не занимается |
| Расписание сузили, пока клиент заполнял | Момент не входит в расписание — отказ с тем же текстом |
| Принятая заявка оказалась вне нового расписания | Не трогаем: время в `scheduled_at`, окно больше не предлагается |
| Свободных окон нет совсем | Вместо формы — «Сервис пока не открыл время для записи» |
| Подделанный момент в payload | Отвергается проверкой принадлежности расписанию |
| Старые заявки без времени | Строка времени в карточке не выводится |

## Проверка

Без базы (`schedule.py` — чистая функция, `validators.py`):

- окна нарезаются шагом от начала рабочего дня и не вылезают за его конец;
- окно, задевающее обед, выброшено;
- дни вне `weekdays` пропущены;
- горизонт соблюдён, прошедшее время не предложено;
- занятость вычитается, при `capacity > 1` окно живёт до последнего места;
- день без свободных окон в результат не попадает;
- время считается в зоне сервиса, а не сервера;
- валидаторы часов, обеда, вместимости, горизонта — тестами вперёд кода.

Против базы:

- две параллельные попытки на одно место дают одну заявку и один отказ;
- отмена и отказ возвращают время в список, `done` — держит навсегда;
- мягко удалённая заявка освобождает время;
- бэкфил заводит расписание всем существующим сервисам;
- правка расписания сохраняется и переживает перечитывание.

Ручная проверка в Telegram — по чек-листу в плане реализации.
