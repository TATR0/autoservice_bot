# Подписка сервиса: срок, гейты и напоминания — дизайн

Дата: 2026-08-23

## Задача

Автосервис платит за бота. Что делать с тем, кто платёж пропустил.

Итерация закрывает жизненный цикл подписки: пробный период, срок оплаты,
отключение продажи нового времени после просрочки, напоминания владельцу и
ручное продление. Приём денег — следующая итерация; здесь готовится место, в
которое она встанет.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Как хранится подписка | Одно поле `services.paid_until`. Активна ⇔ `paid_until > now()` |
| Отдельный статус подписки | Нет. Состояние выводится, а не переключается |
| Колонка `plan` | Не читаем и не пишем. Оживёт, когда появятся разные тарифы |
| Пробный период | 5 дней. Проставляется в `paid_until` при регистрации, отдельной сущности нет |
| Что отключает просрочка | Только продажу нового времени: поиск, форму, приём заявок |
| Что просрочка не трогает | Кабинет управляющего, уже записанных клиентов, их заявки и уведомления |
| Удаление за неуплату | Не бывает. Только кнопкой «удалить сервис» |
| Слышит ли клиент про оплату | Нет. Ему — «сервис не принимает онлайн-запись» и телефон |
| Напоминания | За 5 дней, за 24 часа и в момент истечения |
| Чем будятся напоминания | Внешний cron дёргает `POST /internal/subscriptions/tick` |
| Идемпотентность напоминаний | Таблица отметок, ключ `(idservice, paid_until, stage)` |
| Продление | Пишется в журнал `subscription_payments`, срок и журнал — одна транзакция |
| Кто продлевает сейчас | Владелец бота командой `/extend`, `source = 'manual'` |

## Что сознательно вне области

- Приём денег: провайдер, чеки, вебхук платежа. Ради него заводится журнал с
  уникальным `external_id`, но самого приёма здесь нет.
- Автопродление, возвраты, отмена платежа.
- Разные тарифы и лимиты по тарифу — поэтому `plan` не трогаем.
- История платежей в интерфейсе управляющего.
- Уведомление управляющему об успешном продлении: пока продление ручное, он
  узнаёт о нём от того, кто его сделал.
- Автоудаление давно неплативших сервисов.

## Архитектура

Три слоя, граница между ними та же, что у расписания.

**`subscription.py` — чистый расчёт.** Ни базы, ни сети, как `slots.py`.
Активность, продление, определение причитающейся стадии напоминания. Вся
арифметика дат живёт здесь и тестируется без базы.

**`database.py` — запросы.** Фильтр `paid_until > now()` в поиске, продление в
транзакции, выборка кандидатов на напоминание и захват отметки.

**Гейты — в четырёх местах**, каждое узкое и уже существующее.

Ключевое свойство: тик **не меняет состояние подписки**. Он рассылает
напоминания и пишет отметки об отправленном. Если cron не работал неделю,
гейты всё равно верны — потеряются только напоминания. Задачи, которая обязана
отработать вовремя, иначе всё разъедется, в системе нет.

## Схема данных

### `services.paid_until`: `date` → `timestamptz`

Истечение и напоминание «за 24 часа» — моменты, а не числа. С `date` пришлось
бы договариваться, в чьей зоне кончается день: у сервисов свои `timezone`, и
«за сутки» превратилось бы в «в полночь накануне по серверному времени».

Колонка сейчас пуста во всех строках — её не пишет ни одна строчка Python, —
поэтому смена типа бесплатна. После первого платежа она такой уже не будет.

```sql
DO $$
BEGIN
    IF EXISTS (SELECT 1 FROM information_schema.columns
                WHERE table_name = 'services' AND column_name = 'paid_until'
                  AND data_type = 'date') THEN
        ALTER TABLE services ALTER COLUMN paid_until TYPE timestamptz;
    END IF;
END $$;
```

### Журнал продлений

```sql
CREATE TABLE IF NOT EXISTS subscription_payments (
    idpayment   uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    idservice   uuid        NOT NULL REFERENCES services(idservice) ON DELETE CASCADE,
    days        integer     NOT NULL,
    paid_until  timestamptz NOT NULL,   -- каким срок стал после этого продления
    source      text        NOT NULL DEFAULT 'manual',
    external_id text,                   -- id платежа у провайдера, NULL для ручных
    granted_by  bigint,                 -- Telegram id продлившего вручную
    createdate  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_subscription_payments_service
    ON subscription_payments (idservice, createdate DESC);

-- Ради этого журнал заводится сейчас, а не вместе с провайдером: повторная
-- доставка того же платежа упрётся в индекс и не продлит подписку дважды.
-- Вебхуки повторяются всегда, это не редкий случай
CREATE UNIQUE INDEX IF NOT EXISTS idx_subscription_payments_external
    ON subscription_payments (source, external_id) WHERE external_id IS NOT NULL;

ALTER TABLE subscription_payments DROP CONSTRAINT IF EXISTS chk_subscription_payments_days;
ALTER TABLE subscription_payments ADD  CONSTRAINT chk_subscription_payments_days
    CHECK (days > 0);
```

`paid_until` в строке журнала — не дубль поля сервиса, а ответ на вопрос «что
это продление дало». Без него на «почему у сервиса такой срок» отвечать нечем.

### Отметки об отправленных напоминаниях

```sql
CREATE TABLE IF NOT EXISTS subscription_reminders (
    idreminder uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    idservice  uuid        NOT NULL REFERENCES services(idservice) ON DELETE CASCADE,
    paid_until timestamptz NOT NULL,
    stage      text        NOT NULL,
    createdate timestamptz NOT NULL DEFAULT now()
);

-- Один и тот же сервис, один и тот же срок, одна и та же стадия — одно письмо.
-- Повторный тик, два тика внахлёст, перезапуск посреди рассылки упираются сюда
CREATE UNIQUE INDEX IF NOT EXISTS idx_subscription_reminders_once
    ON subscription_reminders (idservice, paid_until, stage);

ALTER TABLE subscription_reminders DROP CONSTRAINT IF EXISTS chk_subscription_reminders_stage;
ALTER TABLE subscription_reminders ADD  CONSTRAINT chk_subscription_reminders_stage
    CHECK (stage IN ('5d','24h','expired'));
```

В ключ входит сам `paid_until`. Отсюда два свойства даром: после продления
новый срок получает свои напоминания, а напомнить повторно про старый срок
невозможно.

### Бэкфил — обязателен

У всех существующих сервисов `paid_until` пуст. В момент выката каждый из них
окажется просроченным: пропадёт из поиска, перестанет принимать заявки. Тихо,
среди рабочего дня.

```sql
-- Живым сервисам — срок вперёд, дальше продлеваются командой /extend.
-- WHERE paid_until IS NULL: повторный прогон схемы никому ничего не перепишет
UPDATE services SET paid_until = now() + interval '30 days'
 WHERE idrecstatus = 0 AND paid_until IS NULL;
```

## Расчёт (`subscription.py`)

```python
def is_active(paid_until: datetime | None, now: datetime) -> bool:
    return paid_until is not None and paid_until > now


def extend(paid_until: datetime | None, now: datetime, days: int) -> datetime:
    """
    Новый срок после продления на days дней.

    Отсчёт от большего из now и текущего срока: заплатил заранее — дни
    прибавляются к остатку и не сгорают; заплатил после просрочки — отсчёт с
    сегодня, иначе оплата уходит в оплату уже прошедшего простоя.
    """
    base = max(now, paid_until) if paid_until else now
    return base + timedelta(days=days)


def due_stage(paid_until: datetime, now: datetime) -> str | None:
    """Какое напоминание причитается прямо сейчас. None — ещё рано."""
```

`due_stage` отдаёт самую позднюю подошедшую стадию: `expired`, когда срок
прошёл, `24h` — в последние сутки, `5d` — за `REMIND_LEAD_DAYS` (пять) дней.
Это константа `subscription.py`, а не `TRIAL_DAYS`: сегодня оба равны пяти, но
означают разное — длину пробного периода и заблаговременность. Пропущенные
стадии не досылаются: если cron молчал двое суток и сервис успел истечь,
управляющий получит «истекла», а не «осталось 24 часа» вдогонку.

## Гейты

| Точка | Файл | Поведение при просрочке |
|---|---|---|
| Поиск по городу | `database.py` `get_services_by_city` | `AND paid_until > now()` в запросе |
| Ссылка `?start=SVC_…` | `handlers/start.py` `_handle_service_link` | «Онлайн-запись недоступна» + телефон сервиса |
| Отдача формы | `app.py` `/api/service/{id}` | 403 с текстом для клиента, не 404 |
| Приём заявки | `handlers/requests.py` `create_request_flow` | `RequestRejected` сразу после `db.get_service` |

Ссылку клиент мог сохранить или получить от знакомого — фильтр поиска её не
прикрывает, поэтому проверка в `_handle_service_link` не дублирующая. Телефон
там даётся ровно как в соседней ветке, где форма не сконфигурирована: клиент
записывается голосом, сервис не теряет заказ из-за биллинговой механики.

403, а не 404: «сервис не найден» — неправда, а неправда стоит вечера отладки.

Проверка в `create_request_flow` — та же линия обороны, что проверка услуг и
проверка окна: форму можно обойти, поэтому решает сервер. Заодно закрывает
клиента, у которого форма была открыта в момент истечения.

**`db.get_service` фильтра не получает.** Иначе управляющий потеряет доступ к
собственному кабинету и не сможет заплатить — ровно та ошибка, из-за которой
отвергнут вариант с `idrecstatus = -1`.

## Владелец сервиса видит своё состояние

Строка в главном меню (`handlers/common.py` `show_main_menu`), текст собирает
`render.subscription_line(svc)`. Молчит, пока до конца срока далеко; за пять
дней сообщает срок; после истечения — что сервис скрыт из поиска и новые
записи не принимаются.

Кнопки продления в этой итерации нет: нажимать ей пока не на что. Вместо неё в
строке контакт из `SUPPORT_CONTACT`. Кнопка появится вместе с провайдером.

## Напоминания

**Эндпоинт.** `POST /internal/subscriptions/tick`, секрет в заголовке
`X-Tick-Secret`, сверяется через `hmac.compare_digest`. Отдельная переменная
`TICK_SECRET`, а не `WEBHOOK_SECRET`: ротация одного не должна ломать другое.
Секрет заголовком, а не в пути, как у `/webhook/{secret}` — там формат навязан
Telegram, а свой cron мы контролируем и незачем светить секрет в access-логах.

Пустой `TICK_SECRET` — эндпоинт отвечает 401 всегда. Иначе на стенде без
настроенного секрета он оказался бы открыт всем.

Крон на VPS, раз в час:

```
0 * * * * curl -fsS -X POST -H "X-Tick-Secret: $TICK_SECRET" https://<host>/internal/subscriptions/tick
```

Точности до часа для суточного напоминания хватает с запасом.

**Что делает тик.** Выбирает кандидатов, считает стадию, пытается захватить
отметку, при успехе отправляет:

```sql
SELECT idservice, service_name, owner_id, paid_until
  FROM services
 WHERE idrecstatus = 0
   AND paid_until IS NOT NULL
   AND paid_until > now() - interval '30 days'
   AND paid_until < now() + interval '5 days'   -- REMIND_LEAD_DAYS
```

Нижняя граница держит выборку узкой: давно истёкшие сервисы своё уже получили,
и перебирать их каждый час незачем.

```python
if not await db.claim_reminder(idservice, paid_until, stage):
    continue          # уже отправляли
await safe_send(bot, owner_id, text)
```

Порядок «сначала отметка, потом отправка» выбран сознательно: при сбое теряется
одно напоминание, а не управляющий получает спам. `safe_send` ретраит сам и
наружу не бросает.

**Адресат — владелец** (`services.owner_id`). Администраторы не платят и на
подписку не влияют.

**Текст** называет срок, говорит про исчезновение из поиска и остановку новых
записей и **отдельной строкой** — что уже записанные клиенты своё время
сохранят. Без неё управляющий решит, что теряет всю запись на неделю вперёд.

**Напоминание за 5 дней и пробный период совпадают.** Триал длится ровно пять
дней, поэтому стадия `5d` подошла бы в секунду регистрации. `create_service` в
той же транзакции вставляет отметку `5d` как уже отправленную, а дату окончания
называет приветствие при регистрации. Тик про неё больше не вспомнит.

## Продление

```python
async def extend_subscription(
    self, idservice: str, *, days: int, source: str = "manual",
    external_id: str | None = None, granted_by: int | None = None,
) -> datetime:
```

Одна транзакция: `SELECT paid_until … FOR UPDATE` (два продления подряд не
должны считать от одного и того же остатка — тот же приём, что при вставке
заявки), расчёт через `subscription.extend`, `UPDATE services`, `INSERT` в
журнал. Иначе однажды появится подписка без следа в журнале либо запись о
платеже, который ничего не продлил.

**Команда `/extend <idservice> <дней>`** в новом `handlers/subscription.py`.
Отвечает новым сроком. В `set_my_commands` не публикуется: в меню у всех она не
нужна, а работает и без публикации.

**Авторизация — `BOT_OWNER_IDS`**, список Telegram id через запятую.
Напрашивалось взять готовый `MASTER_CHAT_ID`, но это чат для недоставленных
уведомлений и вполне может оказаться группой: у группы id отрицательный и с
user id не совпадёт никогда — проверка молча перестала бы пускать всех. Разные
вещи, разные переменные. Список, а не одно значение, — чтобы был запасной
аккаунт.

## Конфигурация

| Переменная | Смысл |
|---|---|
| `TICK_SECRET` | Секрет эндпоинта напоминаний. Пусто — эндпоинт закрыт |
| `BOT_OWNER_IDS` | Telegram id владельцев бота через запятую, для `/extend` |
| `SUPPORT_CONTACT` | Куда писать за продлением, показывается управляющему |
| `TRIAL_DAYS` | Пробный период, по умолчанию 5 |

## Граничные случаи

| Случай | Поведение |
|---|---|
| Срок истёк, пока клиент заполнял форму | Отказ при отправке заявки, текст без слова «подписка» |
| Клиент записан на завтра, срок истёк сегодня | Заявка жива, время за клиентом, управляющий её видит |
| Cron не работал неделю | Гейты верны, напоминания за этот период потеряны |
| Два тика внахлёст | Уникальный индекс отметок, письмо одно |
| Продление до истечения | Дни прибавляются к остатку |
| Продление после истечения | Отсчёт с `now()`, простой не оплачивается |
| Повторный вебхук платежа (в будущем) | Уникальный `(source, external_id)`, второго продления нет |
| `paid_until IS NULL` | Сервис неактивен, напоминания не шлются: напоминать не о чем |
| Просроченный сервис у управляющего | Кабинет открыт полностью, включая расписание и заявки |

## Проверка

**Без базы** (`tests/test_subscription.py`, мгновенные, как `test_slots.py`):
активность на границе срока; продление вперёд от остатка и от `now()` после
просрочки; стадия напоминания на каждом отрезке, включая пропуск стадий при
долгом молчании крона.

**По базе** (`tests/test_schedule.py`-стиль, против настоящего PostgreSQL):
просроченный сервис не находится в поиске, но `get_service` его отдаёт;
продление пишет срок и журнал одной транзакцией; повторный захват отметки той
же стадии не проходит; заявка в просроченный сервис отклоняется; повторная
вставка платежа с тем же `external_id` упирается в индекс.

**По HTTP** (`tests/test_api_security.py`-стиль, без lifespan): тик без секрета,
с пустым и с чужим секретом отвечает 401; форма просроченного сервиса не
отдаёт расписание.

**Главное свойство:** два тика подряд шлют ровно одно сообщение.
